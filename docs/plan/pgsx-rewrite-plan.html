PGS Atlas rewrite: Go, React, Postgres, muranoq

A plan to rebuild pgsviz.compgenlab.org on the paperKB stack. It reaches feature parity, keeps sample-level data on the server, and adds a managed way to compute and load new scores with pgsc_calc on Slurm.

Decisions so far

Name

PGS Atlas. The binary, config and job-type prefix are pgsatlas.

Dataset

A group of samples processed the same way (genotyping, imputation, QC and pgsc_calc run), and therefore comparable. It is the unit of access and of comparison.

Re-score everything

There are new PGS available, so every dataset, including the one holding today's 37,948 samples, is re-run through pgsc_calc. No scores are migrated from the old site.

Stack

Go API with a React Router v7 SSR frontend, following paperKB's conventions. Postgres for application data.

Queue

muranoq, on its Postgres backend (assumed done). Async site work and Slurm jobs both go through it.

Open and private datasets

Access is set per dataset. 1000 Genomes is open to anyone, with no login, so the site can be shown for publication. The three biobank datasets are private to biobank users.

Logins

There are three ways to sign in: a signed biobank JWT, CILogon (OIDC), or a local username and password (bcrypt). Each dataset lists which identity providers grant access. The biobank's JWT issuer is configured to grant all three biobank datasets, and another institution could be added as its own issuer the same way. A biobank JWT carries a user identity, and any valid one grants access to the biobank datasets. The other two only grant what an admin assigns.

Within-dataset only

A sample can only be compared with other samples in the same dataset. Each analysis runs on exactly one dataset.

Return to the biobank

For now, a list of participant IDs: the top X% of a cohort for a chosen PGS. It goes to the biobank only, server to server, and is never shown in the browser. Returning per-sample scores comes later, when the biobank wants it.

Privacy floor

On protected datasets, cohorts and cells need at least 10 samples (configurable per dataset), and there are no dataset-wide views. The open 1KG demo can also show sample-level views. Aggregate results don't need governance sign-off.

Lead

Score-to-data, as a deployable service. Anyone with access can run their own score against private genotypes and get privacy-gated aggregates back. Any biobank can run the service behind its own login.

One score pipeline

New PGS Catalog scores and user-uploaded scores go through the same steps: stage, validate, approve, batch, pgsc_calc, ingest. Only the source and the visibility differ.

Admin role

Admins mainly define datasets: a declarative YAML file per dataset covering build, pinned pgsc_calc version and reference panel, privacy, access, and user-score policy. Releases, scoring and ancestry groups follow from that file.

User scores

Admin approval for now. Once approved, a request is submitted to the cluster immediately, with no waiting for a batch. Overnight turnaround is fine, since Slurm queue time varies.

Core workflow

Score a dataset, then form smaller cohorts from sample lists users bring (usually from the biobank). Compare different PGS between cohorts, or the same PGS between cohorts. The public 1KG side is a demo.

Refresh cadence

Latest PGS Catalog and latest pgsc_calc, refreshed at least every 6 months. Each refresh is a new release of every dataset, scored through the normal pipeline.

Deferred

Biobank JWT details (issuer, JWKS, audience, login start) and the return credential flow are settled later. Until then, development uses local and CILogon logins with admin grants.

Scope v1

Feature parity, the score pipeline including user uploads, and packaging another site can install.

Compute

Two kinds of worker. One or two always-on analysis workers run queries and analyses and return results to the web. A Slurm delegate submits HPC jobs, such as pgsc_calc for one dataset's VCFs with a score matrix.

Genotypes

Each dataset's VCFs sit in a fixed location on the cluster. Jobs name the dataset, and the delegate's config maps that name to paths. Paths never appear in a payload, and VCFs never go to S3.

Demo data

The latest 1000 Genomes 30× WGS release (NYGC high coverage, GRCh38).

Queue SDK

pgsatlas uses muranoq-go: worker for the analysis workers, client for the API and the Slurm delegate. muranoq-go goes public before pgsatlas ships. Until then, development builds use GOPRIVATE=github.com/muranohq/*, and CI uses a deploy key.

Config

YAML (pgsatlas.yaml). Precedence is flag, then env, then file.

Hosting

Kubernetes on Jetstream2 at IU, in one namespace that includes Postgres. Ingress is Traefik. Compute nodes can reach the S3 buckets with the operator's credentials on that server.

Name and positioning

The name is PGS Atlas. pgsviz.compgenlab.org stays as a redirect. The binary, config file and muranoq type prefix are pgsatlas. The repository can be renamed to compgenlab/pgs-atlas (GitHub redirects the old URL) whenever that's convenient.

Searches on 2026-11-19 found two related tools:

  • PGSXplorer (PeerJ, 2025) is a Nextflow pipeline for PGS QC and model development. It's the reason to drop "PGS Explorer".
  • PGS Browser (Nat Commun) shows reference distributions for about 3,168 PGS across 473k FinnGen participants. It does "browse score distributions in a big biobank" at a larger scale than we can.

What would make PGS Atlas different (draft for discussion)

Browsing precomputed distributions is no longer new, and a site that lets one biobank's users log in isn't a paper by itself. These are the angles where the design above could support a real claim. Each one shifts what v1 should prioritise.

Target architecture

The API server does no computation. It authenticates, checks the results cache, and submits work. All computation runs on one of two kinds of worker, both fed by muranoq:

Analysis workersSlurm delegate
Commandpgsatlas worker, always on, 1–2 instancespgsatlas slurm-delegate --once, run from cron on the cluster
Job typespgsatlas.analysis.* (interactive), then ingest, summarize, catalog sync and export (bulk)pgsatlas.hpc.*, starting with pgsatlas.hpc.pgsc_calc
LatencyMilliseconds to seconds, while the user waitsMinutes to hours, with status every 10 minutes
Built onmuranoq-go worker package (Run)muranoq-go client calls with a state file
Data accessPostgres (score vectors, results) and S3Each dataset's VCFs on the cluster filesystem, plus S3 (score matrices in, results out) with the operator's credentials

With scores stored as vectors, a histogram, KDE or odds ratio over 38k values takes milliseconds. So an always-on worker can answer an interactive request almost as fast as the API could do it in-process, and the compute stays out of the web tier.

  • One Go binary, pgsatlas, with subcommands: serve, worker, slurm-delegate, initdb, migratedb, dataset, cohort, score, ingest, user, apikey and job. This matches the shape of cmd/paperkb.
  • Separate frontend service (frontend/), on React Router v7 SSR. Loaders call /api/v1 and forward the session cookie. On Kubernetes, the ingress routes /api to the Go service and everything else to the frontend, so the app stays same-origin (Caddy only in local compose).
  • muranoq is a separate service in its own Postgres schema or database. The app keeps a jobs row that mirrors each muranoq job ID, so the UI can list a user's work without asking muranoq for it.
  • S3 holds bulk data: pgsc_calc inputs and outputs, ingest staging files, exports and large precomputed artifacts. Postgres holds everything the API reads.

Repo layout

The layout follows paperkb/paperkb, with one change: configuration is YAML (pgsatlas.yaml) instead of paperKB's TOML. Precedence stays flag, then env, then file. Its other CLAUDE.md conventions carry over: goose migrations that are never edited once merged, snake_case DTOs with a contract test, store files split by concern, and CI running gofmt, vet, golangci-lint, build and test. paperKB's navy, brass and parchment look is its own brand, so PGS Atlas gets a separate identity.

Data model

Terms

TermMeansExamples
DatasetA group of samples processed the same way (genotyping, imputation, QC, pgsc_calc run), and therefore comparable. It has its own VCFs and its own access policy, and it is the unit of access and of comparison.1kg-30x (open), and three biobank datasets (private)
CohortA set of samples within one dataset that a user brings to compare, usually from a biobank participant list. Comparisons are between cohorts, or between PGS within a cohort."T2D cases · biobank-a", "controls · biobank-a"; 1KG populations in the demo
ReleaseAn immutable version of a dataset's sample list and scores. Analyses pin to a release.biobank-a@2
ParticipantA biobank person. One participant can have samples in more than one dataset.samples.participant_id

Importing a biobank participant list (what the biobank calls a cohort) maps participants to samples in every dataset the user can access. It creates one cohort per dataset where any of them appear, for example "T2D cases · biobank-a" and "T2D cases · biobank-b". Each group shows only its size. Groups below the dataset's minimum are kept but marked too small to analyse, and participants found in no dataset are counted, never listed. Because analyses stay within one dataset, the same person can never be counted twice in one comparison.

Scores as vectors, not rows

Each sample in a dataset release gets a fixed index. Each (release, PGS, score type) is one row holding a real[] of length N, aligned to that index, with NaN for missing values. Cohorts become sorted sets of sample indexes. Because a vector belongs to exactly one dataset, the within-dataset rule falls out of the layout: there's no way to put samples from two datasets in one series.

LayoutRowsSize (approx.)Read one PGS for 3 cohorts
Today: long table≈ 660M40–60 GB with indexesIndex scan of 38k rows plus an IN filter
Proposed: vectors≈ 17k per 38k-sample dataset≈ 2.6 GB (38k × 4 B × 17k)One 150 KB row, then gather by index in Go

Each row is TOASTed and compressed once. Workers cache hot vectors in memory with an LRU keyed by row ID and release. Writes only happen at ingest, so caching is simple.

1000 Genomes 30× as the open dataset

  • The NYGC high-coverage release has 3,202 samples: the 2,504 unrelated phase 3 samples plus 698 relatives (602 complete trios), in 26 populations and 5 superpopulations, on GRCh38.
  • The built-in cohorts are the superpopulations, the populations, and "unrelated" (2,504), which is the default for distributions.
  • 1KG has no phenotypes, so any demo case/control groups are synthetic or population-based, and the UI labels them as such.
  • Caveat for the paper: pgsc_calc's ancestry reference panel is itself built from 1KG (with HGDP). The 1KG samples are therefore normalized against a panel that contains them, so their Z-scores need to be read and described with that in mind.

Moving off the current site: nothing is migrated. Every dataset, including the one that holds today's 37,948 samples, gets a fresh first release from new pgsc_calc runs with the current PGS Catalog set. The old site's scores are kept only as a reference for the cutover sanity check. Sessions, tasks and temporary uploads are dropped.

  • One check, everywhere. Each request goes through access.Resolve(session, dataset) before any cache lookup or job submission. A dataset the caller can't see answers 404, and it doesn't appear in listings or search.
  • Jobs carry the decision. The API puts the caller's resolved access in the job payload, and the worker checks it again against dataset_grants before reading vectors. A queued job can't outlive a revoked grant by more than one check.
  • Cohort import uses the signed-in user's biobank token, server to server, against the configured biobank base URL. Nothing about the API location comes from the request.

Privacy rules

Each dataset has a privacy profile, and every response that touches score values goes through internal/privacy with that profile. Handlers never serialize raw vectors themselves.

Ruleopen (1KG)protected (biobank)
Minimum group or cell size110 by default, configurable per dataset
Histogram and odds-ratio bins below the minimumShownMerged with a neighbour, or suppressed and labelled
Box plotsOutlier points and min/max shownNo outlier points. Whiskers at p1/p99.
Sample-level views (per-sample PCA/UMAP, sample lookup, per-sample CSV)AllowedNever
Sample IDs in responsesAllowed (they're public)Never
Differencing between overlapping groupsNot applicableCase and control must be disjoint, or the overlap is reported and dropped. Requests are audit-logged. Optionally, refuse a group whose symmetric difference with another of the user's groups is below the minimum.
  • Users cannot create cohorts from arbitrary ID lists on protected datasets. Cohorts come from the biobank import or from admins.
  • No dataset-wide views on protected datasets. There is no "ALL" cohort and there are no built-in ancestry cohorts there. A dataset can also set max_cohort_fraction (for example 0.5) so an imported list can't stand in for the whole dataset. Ancestry is still available inside a cohort, to stratify or filter it, subject to the minimum cell size.
  • The cache key includes the privacy profile, so a result computed under open rules can never be served for a protected dataset.
  • User-uploaded scores get visibility: owner. Only the uploader and admins see them, under the dataset's normal privacy profile.
  • Rules for user scores on protected datasets. A crafted score is a genotype query in disguise. A score that puts its weight on one or a few variants turns a distribution into genotype counts, and differencing between groups could then point to individuals, as in beacon attacks. So score.validate rejects a user score unless all of the following hold, with thresholds configurable per dataset:
    • It has at least a minimum number of variants (for example 50).
    • Its effective number of variants, neff = (Σ|w|)² / Σw², is above a floor.
    • No single variant carries more than a set share of the total absolute weight.
    Quotas, approval and the audit log back this up. Catalog scores with very few variants are public, but the minimum group size and bin suppression still apply to them.

Beyond parity (after v1)

  • Trait view: all PGS for an EFO trait side by side, with distributions, case/control separation, variant match rate, development ancestry, and the correlation between scores.
  • Portability: per-ancestry mean and variance shifts for every score: precomputed on open datasets, computed within a user's cohort on protected ones.
  • Multivariate, done safely: a PGS × PGS correlation matrix per cohort, with clustering and PCA of the scores. These are aggregates, so they work on protected datasets. On the open 1KG dataset, the per-sample PCA, UMAP and heatmap views can come back as they were.
  • Covariate-adjusted models (age, sex, PCs), if the biobank can supply covariates through the same server-side path.

One score pipeline

Adding a score from the PGS Catalog and a user bringing their own score are the same process. Only two things differ: where the scoring file comes from, and who can see the results. There is one pipeline, one set of job types and one data model for both, so the score-to-data feature isn't a separate system to build and maintain.

Defining a dataset: the main admin job

Because every score goes through the same pipeline, an admin's main job is defining datasets. Everything else (scoring, ancestry groups, summaries) follows from the definition. A dataset is a YAML file applied with pgsatlas dataset apply -f. It's declarative, so it can be kept in version control at each site.

# datasets/biobank-a.yaml
slug: biobank-a
name: "Biobank cohort A"
description: "…"
genome_build: GRCh38
scoring:
  pgsc_calc_version: "2.x.y"      # pinned per release
  ref_panel: "pgsc_HGDP+1kGP_v1"   # pinned per release
  catalog: all                     # or a filter (min match rate, traits, list)
privacy:
  profile: protected               # open | protected
  min_cell: 10
access:
  providers: [biobank]             # trusted JWT issuers that grant this dataset
  users: []                        # extra named grants (CILogon, local)
user_scores:
  accepted: true
  need_approval: true
  min_variants: 50
  min_n_eff: 20
  max_variant_weight_share: 0.05
  quota: { scores_per_request: 20, runs_per_month: 10 }
biobank_return: true               # top-X% participant lists may go back to the biobank
max_cohort_fraction: 0.5           # protected: no cohort may cover more than half the dataset
samples: s3://…/datasets/biobank-a/samples.tsv   # sample_id, participant_id, sex
  • The cluster half: the delegate's own config maps biobank-a to its VCF path pattern. The app never sees paths.
  • Ancestry comes free: pgsc_calc's --run_ancestry output assigns each sample its most similar reference population, and ingest stores it on samples. On the open 1KG dataset these become built-in cohorts, alongside 1KG's own population labels. On protected datasets they are only used to stratify or filter users' cohorts.
  • Lifecycle:
    1. apply creates or updates the definition.
    2. release create starts a release in loading and files a system score request for every Catalog score matching scoring.catalog.
    3. The pipeline runs.
    4. release promote makes it active, after an admin looks at QC (match rates, failures).
    5. release retire retires the old one.
    Changing pgsc_calc_version or ref_panel requires a new release.
  • The admin UI is mostly for viewing and approving: datasets and their releases and QC, pending user-score approvals, jobs, and the audit log. Definitions change through the CLI or API, so they stay reviewable.

What "deployable" means for v1

  • One install: a kustomize package (Helm if asked for) with Postgres, muranoq, the API, the frontend, the workers and the ingress. A second site changes only configuration.
  • Site configuration only: the trusted JWT issuers, the S3 bucket, branding, and one dataset file per dataset (above). No code changes for a new site.
  • The cluster side is one config file: the delegate's pgsatlas.yaml maps dataset slugs to VCF paths and builds, plus an sbatch template the site edits for its own partitions and modules.
  • 1000 Genomes 30× in every install: a scripted fetch and score of 1KG gives each new site a working open dataset on day one. It's also the reference that results from different sites can be checked against.
  • Docs written for an outside operator, tested by standing up a clean install from them.

Jobs and the queue

Everything runs in one muranoq namespace, pgsatlas. The app submits jobs with a submit account. The analysis workers and the Slurm delegate each use their own work account. Every job is tagged user:<id> and dataset:<slug>.

QueueWeightServed byLimits
interactive80Analysis workerstime_limit 60 s, no retries beyond 1
bulk20Analysis workersEvery bulk job shares concurrency_key: pgsatlas-bulk with a limit of 1
hpc(own workers)Slurm delegate onlyLong time_limit, lease TTL 30 min

muranoq never preempts a running task. So each analysis worker runs with Concurrency of 4 or more, and the pgsatlas-bulk concurrency key caps bulk work at one slot across the whole pool. An ingest therefore can't take every slot, and interactive requests always find a free one.

An analysis request, end to end.

  1. The API normalizes the request and checks dataset access, and computes its cache key (request, release, privacy profile, cohort member hashes).
  2. On a hit, it returns the cached result straight away.
  3. On a miss, it submits pgsatlas.analysis.* to interactive with idempotency_key set to the cache key, so identical concurrent requests share one job. It then waits up to about 3 s with client.Wait.
  4. If the job finishes in that time, the API returns the result inline. Otherwise it answers 202 with the job ID, and the page polls /api/v1/jobs/{id} (SSE later).
  5. The worker applies internal/privacy before writing the result, so nothing below the minimum cell size reaches the cache, muranoq or the browser.

The analysis worker. pgsatlas worker is built on the muranoq-go worker package. It creates a worker.New(client, worker.Config{Name, Concurrency, Capacity}), registers a handler for each type with w.Handle("pgsatlas.ingest", …), and runs w.Run(ctx). The SDK handles registration, claiming within free capacity, lease heartbeats, stop/cancel signals, and deregistration on SIGTERM. Handlers just decode the payload, use the task ref as their idempotency key, report progress with t.Progress(…), and return either a result or an error: worker.Terminal(err) for bad input, worker.Retry(err, d) for a retry after a delay. The API server uses muranoq-go/client to submit jobs (with an idempotency key and tags) and to read their state. Connection settings come from MURANOQ_URL and MURANOQ_TOKEN_FILE, or from the muranoq: block in pgsatlas.yaml.

Chaining. pgsc_calc → ingest → summarize runs as a dependency chain, or as follow-on jobs if muranoq's M2 lands first. Until then, a reconciler loop in pgsatlas worker watches the app's jobs rows and submits the next step. The same loop mirrors muranoq state into jobs for the UI, using events or SSE once muranoq has them and polling until then.

Adding scores (from the Catalog or a user) is described in One score pipeline. For pgsc_calc outputs already on S3 there is also a direct admin path: pgsatlas ingest pgsc-calc s3://….

Slurm delegate

A cron job on the cluster polls muranoq, submits work to Slurm, and reports status at least every 10 minutes. There is no live heartbeat. Compute nodes never talk to muranoq; they read the dataset VCFs from the cluster filesystem and read and write S3.

One cron tick

# */10 * * * *  flock -n ~/.pgsatlas-delegate.lock pgsatlas slurm-delegate --once
1. register worker (idempotent by name+host)          POST /v1/workers
2. for each tracked task in state dir:
     sacct -j <slurm_id> → PENDING | RUNNING | COMPLETED | FAILED | CANCELLED | TIMEOUT
     PENDING/RUNNING  → heartbeat {progress: {slurm_state, nextflow trace summary}}
                         if response.stop → scancel; record
     COMPLETED        → verify s3://…/runs/<ref>/_SUCCESS → complete {result: {s3_prefix, qc}}
     FAILED/TIMEOUT   → fail {retryable: true|false, error: tail of logs}
3. free = max_inflight − tracked
   claim {max: free, wait: 0}
   for each task: render sbatch from template (time = task.time_limit) → sbatch → save
     {ref, lease_token, slurm_id, submitted_at} to the state dir
  • SDK use: the delegate (pgsatlas slurm-delegate --once) uses muranoq-go/client directly, not the worker package. worker.Run and Close deregister the worker on exit, and muranoq hands a deregistered worker's tasks straight back to ready, which would undo every tick. Instead each tick calls RegisterWorker (idempotent) and never deregisters. It saves each client.Claimed (ref and lease token) to the state file and passes it back to Heartbeat, Complete or Fail on later ticks. client.IsLeaseLost tells it when a saved claim has expired.
  • Leases: the pgsatlas-slurm queue's namespace gets lease_ttl ≥ 3 × cron interval (30 minutes), so two missed ticks don't lose the lease.
  • Idempotency: the task ref names the S3 output prefix and the Slurm job name. A re-run finds and reuses a completed prefix instead of computing again.
  • pgsc_calc on Slurm: the sbatch job runs a Nextflow head process with -profile slurm, which fans out its own Slurm jobs. The delegate tracks the head job, and progress comes from Nextflow's trace file.
  • The pgsc_calc batch script (hpc/pgsc_calc.sbatch):
    1. Looks up the task's dataset in the delegate config (datasets.<slug>.vcf, target_build) and writes the pgsc_calc samplesheet pointing at those VCFs in place. Nothing is copied.
    2. Stages the batch's scoring files from S3 to scratch. Catalog and user files are both already in pgsc_calc's format and are passed unchanged with --scorefile.
    3. Runs pgscatalog/pgsc_calc with --target_build, --pgs_id and/or --scorefile, plus --run_ancestry with the reference panel.
    4. Uploads results/ and a _SUCCESS marker to the run prefix, then cleans up scratch.
  • S3 credentials: the operator's credentials stay on the cluster, as now. Payloads carry only dataset slugs and S3 URIs, never filesystem paths or credentials.
  • Delegate config (pgsatlas.yaml on the cluster): the muranoq URL and token file, S3 bucket, max_inflight, the sbatch template, and a datasets: map from slug to VCF path pattern and genome build. A task for an unknown slug fails as terminal.

What a muranoq delegate mode would add

The tick above works against muranoq as it is. These are the gaps that make a built-in mode worth adding once the cron script has settled the rules.

Gap with plain leasesProposed delegate behaviour
Lease TTL is set per namespace, so long TTLs also apply to ordinary workers.A worker registers with mode: delegate and a report_interval. The server sets that worker's lease TTL to about 3× the interval.
time_limit counts time spent waiting in Slurm's queue.Heartbeats carry an external_state of submitted or running, and the time limit clock starts at running. Queue wait gets its own optional limit.
If the cron dies, the lease expires and the task is retried while the Slurm job may still be running, so it can run twice.An expired delegate lease moves the task to orphaned instead of ready. The next tick from the same worker can adopt it again with the saved external_id; otherwise an operator releases it.
The Slurm job ID is invisible in muranoq status.The task records external_id and external_state, and status shows them.
Every site would write its own state-file glue.muranoq delegate --once --type … --submit 'sbatch …' --status 'sacct …' --cancel 'scancel {id}' --state-dir …. The same shape would work for PBS, LSF or Kubernetes Jobs.

Milestones

P0

Foundations

  • Repo skeleton in the paperKB shape: config, goose baseline, a /api/v1/session endpoint, admin users and API keys.
  • CI: gofmt, vet, lint, test and a migrate-check.
  • Kustomize manifests for one Jetstream2 namespace: Postgres, muranoq (from muranoq's deploy/k8s), API, frontend, worker, and Traefik IngressRoutes (/api to Go, everything else to the frontend). docker-compose for local dev.

Exit: an empty app deploys to Jetstream2 and an admin can log in with a local password.

P1

Data layer

  • Datasets, releases, samples, cohorts, score vectors, and dataset_grants.
  • pgsatlas ingest pgsc-calc from S3.
  • PGS Catalog sync. The first pgsc_calc runs (1KG 30×, then the three biobank datasets) are started by hand on the cluster with the same sbatch template the delegate will use, so ingestion isn't blocked on P4.

Exit: 1KG and the three biobank datasets are freshly scored and loaded, and vector reads are benchmarked.

P2

Analysis parity

  • internal/stats with scipy-checked fixtures.
  • The privacy gate.
  • Distribution and case-vs-control endpoints and pages, the score detail page, and the results cache.

Exit: the open 1KG dataset works end to end with no login, which is enough to show for the paper.

P3

Biobank access

  • Login through configured JWT issuers (the biobank first), per-dataset provider grants, and the access check on every route and job.
  • CILogon login and admin grants to individual users.
  • Server-to-server cohort import (one cohort per dataset the participants appear in), cohort management, top-X% return, and the audit log.

Exit: a biobank user reproduces today's analyses on a biobank dataset, and an anonymous user can't tell those datasets exist.

P4

Score pipeline

  • pgsatlas worker on the muranoq-go worker package, the ingest and summarize handlers, and the reconciler.
  • The pgsatlas slurm-delegate cron job and the pgsc_calc sbatch template.
  • Score requests, fetch, validate (with the user-score rules), approval, batching, pgsc_calc per dataset, ingest. The upload page, "my scores", and admin pages for requests, jobs and datasets.
  • Kustomize package and operator docs. Tested with a clean install that has only 1KG.

Exit: 100 new Catalog scores and one user-uploaded score go through the same path. The user sees their score's distribution and case/control results on a protected dataset; nobody else can see it.

P5

Cutover

  • Run the new site side by side with the old one. For PGS present in both, compare distributions on the dataset that holds the old samples. Expect small differences from the new pgsc_calc version; the check is for gross errors, not equality.
  • Switch DNS and retire the old site.

Exit: pgsviz.compgenlab.org serves the new app.

P6

Beyond parity

  • Trait comparison, portability, aggregate multivariate views (and sample-level ones on 1KG), and per-sample score return to the biobank, once it wants it.
  • A muranoq delegate mode, if the cron job shows the need.

Exit: scoped separately.

Open questions

  1. PGS Catalog filter: score every Catalog score, or drop ones with low variant match rates after a first pass? (Decided: the latest Catalog and the latest pgsc_calc, refreshed at least every 6 months, with each refresh as a new release.)
  2. User score limits on the biobank datasets: which quotas (scores per request, runs per month) and which thresholds for minimum variants, neff and maximum single-variant weight? (Aggregate results don't need governance sign-off.)
  3. A second site: possible but not confirmed. If none materialises before the paper, the fallback evidence is a clean install of a second, 1KG-only site from the operator docs alone, on separate infrastructure, plus the per-dataset issuer model shown with two issuers.
