PGS Explorer rewrite: Go, React, Postgres, muranoq

A plan to rebuild pgsviz.compgenlab.org on the paperKB stack. It reaches feature parity, keeps sample-level data on the server, and adds a managed way to compute and load new scores with pgsc_calc on Slurm.

Decisions so far

Stack

Go API with a React Router v7 SSR frontend, following paperKB's conventions. Postgres for application data.

Queue

muranoq, on its Postgres backend (assumed done). Async site work and Slurm jobs both go through it.

Anonymous mode

A public demo on 1000 Genomes data, with no login.

Biobank login

Users sign in with a JWT issued by the biobank site. Sending data back to the biobank uses an OAuth2 token flow, which is already planned on the biobank side.

No other IdPs

No IU CAS and no CILogon. Admins use local accounts or API keys, and data loading is CLI-first.

Privacy floor

The minimum cohort or cell size is 10 by default and can be configured.

Scope v1

Feature parity, plus a way to add and manage new data: pgsc_calc runs and ingestion.

Compute

Two kinds of worker. One or two always-on analysis workers run queries and analyses and return results to the web. A Slurm delegate submits HPC jobs such as pgsc_calc on a VCF with a set of scoring files.

Config

YAML (pgsx.yaml). Precedence is flag, then env, then file.

Hosting

Jetstream2 at IU. Compute nodes can reach the S3 buckets with the operator's credentials on that server.

What the site does today

Researchers use PGS Visualizer to explore polygenic scores in the Indiana Biobank / AnalytiXIN cohort without seeing individual-level data. With it they can check how a published score behaves here before relying on it. They can see how its distribution shifts across ancestry groups, and get a first look at whether it separates their cases from controls.

Target architecture

The API server does no computation. It authenticates, checks the results cache, and submits work. All computation runs on one of two kinds of worker, both fed by muranoq:

Analysis workersSlurm delegate
Commandpgsx worker, always on, 1–2 instancespgsx slurm-delegate --once, run from cron on the cluster
Job typespgsx.analysis.* (interactive), then ingest, summarize, catalog sync and export (bulk)pgsx.hpc.*, starting with pgsx.hpc.pgsc_calc
LatencyMilliseconds to seconds, while the user waitsMinutes to hours, with status every 10 minutes
Built onmuranoq-go worker package (Run)muranoq-go client calls with a state file
Data accessPostgres (score vectors, results) and S3S3 only, using the operator's credentials on the cluster

With scores stored as vectors, a histogram, KDE or odds ratio over 38k values takes milliseconds. So an always-on worker can answer an interactive request almost as fast as the API could do it in-process, and the compute stays out of the web tier.

  • One Go binary, pgsx, with subcommands: serve, worker, slurm-delegate, initdb, migratedb, dataset, ingest, pgs, user, apikey and job. This matches the shape of cmd/paperkb.
  • Separate frontend service (frontend/), on React Router v7 SSR. Loaders call /api/v1 and forward the session cookie, and Caddy keeps everything same-origin.
  • muranoq is a separate service in its own Postgres schema or database. The app keeps a jobs row that mirrors each muranoq job ID, so the UI can list a user's work without asking muranoq for it.
  • S3 holds bulk data: pgsc_calc inputs and outputs, ingest staging files, exports and large precomputed artifacts. Postgres holds everything the API reads.

Repo layout

The layout follows paperkb/paperkb, with one change: configuration is YAML (pgsx.yaml) instead of paperKB's TOML. Precedence stays flag, then env, then file. Its other CLAUDE.md conventions carry over: goose migrations that are never edited once merged, snake_case DTOs with a contract test, store files split by concern, and CI running gofmt, vet, golangci-lint, build and test. paperKB's navy, brass and parchment look is its own brand, so PGS Explorer gets a separate identity.

Data model

Scores as vectors, not rows

Each sample in a dataset gets a fixed index. Each (dataset version, PGS, score type) is one row holding a real[] of length N, aligned to that index, with NaN for missing values. Cohorts become sorted sets of sample indexes.

LayoutRowsSize (approx.)Read one PGS for 3 cohorts
Today: long table≈ 660M40–60 GB with indexesIndex scan of 38k rows plus an IN filter
Proposed: vectors≈ 17k≈ 2.6 GB (38k × 4 B × 17k)One 150 KB row, then gather by index in Go

Each row is TOASTed and compressed once. The API caches hot vectors in memory with an LRU keyed by row ID and version. Writes only happen at ingest, so caching is simple.

Privacy rules

Every response that touches score values goes through internal/privacy. Handlers never serialize raw vectors. The default minimum is min_cell = 10, configurable per deployment and per dataset. A public dataset such as 1000 Genomes can lower it, but it still goes through the same code path.

  • Cohorts: any cohort with fewer than min_cell members present for the score is refused with a clear message.
  • Histograms and odds-ratio bins: bins below min_cell are merged into a neighbouring bin, or suppressed and labelled as such. Every 2×2 cell in an OR must meet the minimum.
  • No individual values: box plots draw no outlier points and use p1/p99 as whiskers rather than min and max. KDEs are evaluated on a grid and are only returned when n meets the minimum.
  • Differencing: two cohorts that differ by only a few people can reveal those people's scores. Mitigations:
    • Users cannot create cohorts from arbitrary ID lists.
    • Case and control cohorts must be disjoint (or the overlap is reported and dropped).
    • Requests are audit-logged.
    • We could also refuse a cohort whose symmetric difference with another of the user's cohorts is below min_cell.
  • No raw data in caches: cached results hold aggregates only, so a cache hit can never leak more than the original response did.

Beyond parity (after v1)

  • Trait view: all PGS for an EFO trait side by side, with distributions, case/control separation, variant match rate, development ancestry, and the correlation between scores.
  • Portability: per-ancestry mean and variance shifts for every score, precomputed per dataset version.
  • Multivariate, done safely: a PGS × PGS correlation matrix per cohort, with clustering and PCA of the scores. These are aggregates, so they bring back much of what the heatmap view offered without sample-level points.
  • Covariate-adjusted models (age, sex, PCs), if the biobank can supply covariates through the same server-side path.

Jobs and the queue

Everything runs in one muranoq namespace, pgsx. The app submits jobs with a submit account. The analysis workers and the Slurm delegate each use their own work account. Every job is tagged user:<id> and dataset:<slug>.

QueueWeightServed byLimits
interactive80Analysis workerstime_limit 60 s, no retries beyond 1
bulk20Analysis workersEvery bulk job shares concurrency_key: pgsx-bulk with a limit of 1
hpc(own workers)Slurm delegate onlyLong time_limit, lease TTL 30 min

muranoq never preempts a running task. So each analysis worker runs with Concurrency of 4 or more, and the pgsx-bulk concurrency key caps bulk work at one slot across the whole pool. An ingest therefore can't take every slot, and interactive requests always find a free one.

TypeQueue · workerInput → output
pgsx.analysis.distribution, pgsx.analysis.case_controlinteractive · analysisNormalized request → privacy-gated aggregates written to results. The task result is just the result key.
pgsx.hpc.pgsc_calchpc · Slurm delegate{target: VCF(s) on S3 or a dataset version, genome build; scores: PGS Catalog IDs and/or a PGS score matrix on S3; ref panel; run_ancestry} → pgsc_calc outputs under s3://…/runs/{task ref}/
pgsx.ingestbulk · analysisAn S3 prefix of pgsc_calc output or a wide file → validated score_vectors, pgs_qc and a score_set. Idempotent by task ref.
pgsx.summarizebulk · analysisA score set → pgs_summaries for each system cohort. One task per PGS block.
pgsx.catalog_syncbulk · analysisThe PGS Catalog REST API → the pgs table. Runs on a schedule and on demand.
pgsx.biobank_exportbulk · analysisA cohort and score selection → a push to the biobank over OAuth2

An analysis request, end to end.

  1. The API normalizes the request and computes its cache key (request, dataset version, cohort member hashes).
  2. On a hit, it returns the cached result straight away.
  3. On a miss, it submits pgsx.analysis.* to interactive with idempotency_key set to the cache key, so identical concurrent requests share one job. It then waits up to about 3 s with client.Wait.
  4. If the job finishes in that time, the API returns the result inline. Otherwise it answers 202 with the job ID, and the page polls /api/v1/jobs/{id} (SSE later).
  5. The worker applies internal/privacy before writing the result, so nothing below the minimum cell size reaches the cache, muranoq or the browser.

The analysis worker. pgsx worker is built on the muranoq-go worker package. It creates a worker.New(client, worker.Config{Name, Concurrency, Capacity}), registers a handler for each type with w.Handle("pgsx.ingest", …), and runs w.Run(ctx). The SDK handles registration, claiming within free capacity, lease heartbeats, stop/cancel signals, and deregistration on SIGTERM. Handlers just decode the payload, use the task ref as their idempotency key, report progress with t.Progress(…), and return either a result or an error: worker.Terminal(err) for bad input, worker.Retry(err, d) for a retry after a delay. The API server uses muranoq-go/client to submit jobs (with an idempotency key and tags) and to read their state. Connection settings come from MURANOQ_URL and MURANOQ_TOKEN_FILE, or from the muranoq: block in pgsx.yaml.

Chaining. pgsc_calc → ingest → summarize runs as a dependency chain, or as follow-on jobs if muranoq's M2 lands first. Until then, a reconciler loop in pgsx worker watches the app's jobs rows and submits the next step. The same loop mirrors muranoq state into jobs for the UI, using events or SSE once muranoq has them and polling until then.

Adding new data (the new v1 feature):

  1. An admin runs pgsx dataset version create iubb, or picks an existing version.
  2. pgsx pgs compute --dataset iubb@v2 --pgs PGS005000-PGS005200 (or the admin UI) submits pgsx.pgsc_calc.
  3. The job gets as far as Slurm, and its progress shows on the admin Jobs page.
  4. Ingest and summarize run. The new scores appear in loading state, and an admin promotes them to active.
  5. For outputs already on S3 there's a direct path: pgsx ingest pgsc-calc s3://….

Slurm delegate

A cron job on the cluster polls muranoq, submits work to Slurm, and reports status at least every 10 minutes. There is no live heartbeat. Compute nodes never talk to muranoq; they only read and write S3.

One cron tick

# */10 * * * *  flock -n ~/.pgsx-delegate.lock pgsx slurm-delegate --once
1. register worker (idempotent by name+host)          POST /v1/workers
2. for each tracked task in state dir:
     sacct -j <slurm_id> → PENDING | RUNNING | COMPLETED | FAILED | CANCELLED | TIMEOUT
     PENDING/RUNNING  → heartbeat {progress: {slurm_state, nextflow trace summary}}
                         if response.stop → scancel; record
     COMPLETED        → verify s3://…/runs/<ref>/_SUCCESS → complete {result: {s3_prefix, qc}}
     FAILED/TIMEOUT   → fail {retryable: true|false, error: tail of logs}
3. free = max_inflight − tracked
   claim {max: free, wait: 0}
   for each task: render sbatch from template (time = task.time_limit) → sbatch → save
     {ref, lease_token, slurm_id, submitted_at} to the state dir
  • SDK use: the delegate (pgsx slurm-delegate --once) uses muranoq-go/client directly, not the worker package. worker.Run and Close deregister the worker on exit, and muranoq hands a deregistered worker's tasks straight back to ready, which would undo every tick. Instead each tick calls RegisterWorker (idempotent) and never deregisters. It saves each client.Claimed (ref and lease token) to the state file and passes it back to Heartbeat, Complete or Fail on later ticks. client.IsLeaseLost tells it when a saved claim has expired.
  • Leases: the pgsx-slurm queue's namespace gets lease_ttl ≥ 3 × cron interval (30 minutes), so two missed ticks don't lose the lease.
  • Idempotency: the task ref names the S3 output prefix and the Slurm job name. A re-run finds and reuses a completed prefix instead of computing again.
  • pgsc_calc on Slurm: the sbatch job runs a Nextflow head process with -profile slurm, which fans out its own Slurm jobs. The delegate tracks the head job, and progress comes from Nextflow's trace file.
  • The pgsc_calc batch script (hpc/pgsc_calc.sbatch):
    1. Stages the VCF(s) and scoring inputs from S3 to scratch.
    2. Writes the pgsc_calc samplesheet.
    3. Turns a PGS score matrix into PGS Catalog-format scoring files, if one was given.
    4. Runs pgscatalog/pgsc_calc with --target_build, --pgs_id and/or --scorefile, plus --run_ancestry with the reference panel.
    5. Uploads results/ and a _SUCCESS marker to the run prefix, then cleans up scratch.
  • S3 credentials: the operator's credentials stay on the cluster, as now. Payloads carry only S3 URIs, which muranoq requires anyway.

What a muranoq delegate mode would add

The tick above works against muranoq as it is. These are the gaps that make a built-in mode worth adding once the cron script has settled the rules.

Gap with plain leasesProposed delegate behaviour
Lease TTL is set per namespace, so long TTLs also apply to ordinary workers.A worker registers with mode: delegate and a report_interval. The server sets that worker's lease TTL to about 3× the interval.
time_limit counts time spent waiting in Slurm's queue.Heartbeats carry an external_state of submitted or running, and the time limit clock starts at running. Queue wait gets its own optional limit.
If the cron dies, the lease expires and the task is retried while the Slurm job may still be running, so it can run twice.An expired delegate lease moves the task to orphaned instead of ready. The next tick from the same worker can adopt it again with the saved external_id; otherwise an operator releases it.
The Slurm job ID is invisible in muranoq status.The task records external_id and external_state, and status shows them.
Every site would write its own state-file glue.muranoq delegate --once --type … --submit 'sbatch …' --status 'sacct …' --cancel 'scancel {id}' --state-dir …. The same shape would work for PBS, LSF or Kubernetes Jobs.

Open questions

  1. muranoq-go is private, and this repo is public. We've decided to use the SDK for pgsx worker and for submitting jobs. Until muranoq-go is public, building pgsx needs read access to it: GOPRIVATE=github.com/muranohq/* and a deploy key in CI, as muranoq-server does. Anyone outside the lab who clones the repo can't build it until then. Will muranoq-go be made public before pgsx is?
  2. Where do the biobank genotypes live for pgsc_calc? On the cluster filesystem only, or staged in S3? This decides what the pgsx.pgsc_calc payload points at and who can read that bucket.
  3. What does the biobank JWT look like? We need the issuer, the JWKS URL, the audience, and which claims carry dataset entitlements. We also need to know how login starts: a redirect carrying the token, or a token the user pastes.
  4. What goes back to the biobank? Per-sample PGS values for a cohort, or derived flags? This is the only path for sample-level data, so its scope should be explicit.
  5. Which demo data? 1000 Genomes phase 3 (2,504) or high-coverage (3,202)? Which PGS? It has no phenotypes, so the demo case/control cohorts would be synthetic or ancestry-based and labelled as such.
  6. Who can request new scores? In v1, only admins can run pgsc_calc. Should biobank users be able to request specific PGS IDs later, with an approval step?
  7. Deployment target on Jetstream2: docker compose on a VM, as paperKB does, or Kubernetes, as the current pod and volume comments suggest?
  8. Names: the binary and CLI as pgsx, the site title as "PGS Explorer". Keep "PGS Visualizer"?
