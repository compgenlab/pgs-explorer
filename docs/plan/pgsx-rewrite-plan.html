A plan to rebuild pgsviz.compgenlab.org on the paperKB stack. It reaches feature parity, keeps sample-level data on the server, and adds a managed way to compute and load new scores with pgsc_calc on Slurm.

Decisions so far

Stack

Go API with a React Router v7 SSR frontend, following paperKB's conventions. Postgres for application data.

Queue

muranoq, on its Postgres backend (assumed done). Async site work and Slurm jobs both go through it.

Open and private cohorts

Access is set per cohort. 1000 Genomes is open to anyone, with no login, so the site can be shown for publication. The three biobank cohorts are private to biobank users.

Logins

There are three ways to sign in: a signed biobank JWT, CILogon (OIDC), or a local username and password (bcrypt). A biobank JWT carries a user identity, and any valid one grants access to the biobank cohorts. The other two only grant what an admin assigns.

Within-cohort only

A sample can only be compared with other samples in the same cohort. Each analysis runs on exactly one cohort.

Data return

Per sample, the scores for the requested PGS are sent back to the biobank, server to server, over an OAuth2 token flow. Only biobank cohorts can be returned, and only to the biobank.

Privacy floor

Private cohorts need at least 10 samples per group or cell; the number is configurable per cohort. The open cohort can also show sample-level views.

Scope v1

Feature parity, plus a way to add and manage new data: pgsc_calc runs per cohort, and ingestion. Admins run pgsc_calc in v1. Users uploading their own score matrix comes later.

Compute

Two kinds of worker. One or two always-on analysis workers run queries and analyses and return results to the web. A Slurm delegate submits HPC jobs, such as pgsc_calc for one cohort's VCFs with a score matrix.

Genotypes

Each cohort's VCFs sit in a fixed location on the cluster. Jobs name the cohort, and the delegate's config maps that name to paths. Paths never appear in a payload, and VCFs never go to S3.

Demo data

The latest 1000 Genomes 30× WGS release (NYGC high coverage, GRCh38).

Queue SDK

pgsx uses muranoq-go: worker for the analysis workers, client for the API and the Slurm delegate. muranoq-go goes public before pgsx ships. Until then, development builds use GOPRIVATE=github.com/muranohq/*, and CI uses a deploy key.

Config

YAML (pgsx.yaml). Precedence is flag, then env, then file.

Hosting

Kubernetes on Jetstream2 at IU. Compute nodes can reach the S3 buckets with the operator's credentials on that server.

Name

The app has been called both "PGS Explorer" (the repo) and "PGS Visualizer" (the site title, pgsviz.compgenlab.org). A paper is a good moment to pick one name and keep it. A quick search on 2026-11-19 found:

  • PGSXplorer (PeerJ, 2025) is a Nextflow pipeline for PGS QC and model development. "PGS Explorer" would be easy to confuse with it in citations and search. It also clashes with the pgsx binary name used throughout this plan.
  • PGS Browser (Nat Commun) shows reference distributions for about 3,168 PGS in FinnGen. It's the closest existing tool in function, so the paper should set itself apart from it: several cohorts with per-cohort access, a diverse US biobank, user case/control groups, and computing new scores on demand.
  • No tool turned up under "PGS Visualizer", "PGSviz" or "PGS Atlas".
CandidateForAgainst

Target architecture

The API server does no computation. It authenticates, checks the results cache, and submits work. All computation runs on one of two kinds of worker, both fed by muranoq:

Analysis workersSlurm delegate
Commandpgsx worker, always on, 1–2 instancespgsx slurm-delegate --once, run from cron on the cluster
Job typespgsx.analysis.* (interactive), then ingest, summarize, catalog sync and export (bulk)pgsx.hpc.*, starting with pgsx.hpc.pgsc_calc
LatencyMilliseconds to seconds, while the user waitsMinutes to hours, with status every 10 minutes
Built onmuranoq-go worker package (Run)muranoq-go client calls with a state file
Data accessPostgres (score vectors, results) and S3Each cohort's VCFs on the cluster filesystem, plus S3 (score matrices in, results out) with the operator's credentials

With scores stored as vectors, a histogram, KDE or odds ratio over 38k values takes milliseconds. So an always-on worker can answer an interactive request almost as fast as the API could do it in-process, and the compute stays out of the web tier.

  • One Go binary, pgsx, with subcommands: serve, worker, slurm-delegate, initdb, migratedb, cohort, group, ingest, pgs, user, apikey and job. This matches the shape of cmd/paperkb.
  • Separate frontend service (frontend/), on React Router v7 SSR. Loaders call /api/v1 and forward the session cookie. On Kubernetes, the ingress routes /api to the Go service and everything else to the frontend, so the app stays same-origin (Caddy only in local compose).
  • muranoq is a separate service in its own Postgres schema or database. The app keeps a jobs row that mirrors each muranoq job ID, so the UI can list a user's work without asking muranoq for it.
  • S3 holds bulk data: pgsc_calc inputs and outputs, ingest staging files, exports and large precomputed artifacts. Postgres holds everything the API reads.

Repo layout

The layout follows paperkb/paperkb, with one change: configuration is YAML (pgsx.yaml) instead of paperKB's TOML. Precedence stays flag, then env, then file. Its other CLAUDE.md conventions carry over: goose migrations that are never edited once merged, snake_case DTOs with a contract test, store files split by concern, and CI running gofmt, vet, golangci-lint, build and test. paperKB's navy, brass and parchment look is its own brand, so PGS Explorer gets a separate identity.

Data model

Terms

TermMeansExamples
CohortA genotyped population with its own VCFs, its own pgsc_calc runs, and its own access policy. It's the unit of access and of comparison.1kg-30x (open), and three biobank cohorts (private)
Sample groupA subset of one cohort's samplesInferred ancestry groups, 1KG populations and superpopulations, case/control lists imported from the biobank
ReleaseAn immutable version of a cohort's sample list and scores. Analyses pin to a release.biobank-a@2

What the biobank API calls a "cohort" (a participant list) is imported as a sample group inside a cohort chosen by the user. Participant IDs that aren't in that cohort are counted and dropped, and they are never listed back to the user.

Scores as vectors, not rows

Each sample in a cohort release gets a fixed index. Each (release, PGS, score type) is one row holding a real[] of length N, aligned to that index, with NaN for missing values. Sample groups become sorted sets of sample indexes. Because a vector belongs to exactly one cohort, the within-cohort rule falls out of the layout: there's no way to put samples from two cohorts in one series.

LayoutRowsSize (approx.)Read one PGS for 3 sample groups
Today: long table≈ 660M40–60 GB with indexesIndex scan of 38k rows plus an IN filter
Proposed: vectors≈ 17k per 38k-sample cohort≈ 2.6 GB (38k × 4 B × 17k)One 150 KB row, then gather by index in Go

Each row is TOASTed and compressed once. Workers cache hot vectors in memory with an LRU keyed by row ID and release. Writes only happen at ingest, so caching is simple.

1000 Genomes 30× as the open cohort

  • The NYGC high-coverage release has 3,202 samples: the 2,504 unrelated phase 3 samples plus 698 relatives (602 complete trios), in 26 populations and 5 superpopulations, on GRCh38.
  • The system sample groups are the superpopulations, the populations, and "unrelated" (2,504), which is the default for distributions.
  • 1KG has no phenotypes, so any demo case/control groups are synthetic or population-based, and the UI labels them as such.
  • Caveat for the paper: pgsc_calc's ancestry reference panel is itself built from 1KG (with HGDP). The 1KG samples are therefore normalized against a panel that contains them, so their Z-scores need to be read and described with that in mind.

Moving off the current site: the existing wide scores file plus ancestry_groups become the first release of the biobank cohort(s), loaded through pgsx ingest wide. That requires knowing which of the three cohorts each current sample belongs to. Existing anonymous sessions, tasks and temporary uploads are not migrated.

Auth and access

A login says who you are. A cohort_grants row says what you can see. Open cohorts need neither.

Way inHowGrants
AnonymousNo login. A rate-limited, read-only API.Open cohorts only.
Biobank JWTThe biobank site sends a signed JWT carrying a user identity. POST /api/v1/auth/biobank checks it against the biobank's JWKS (iss, aud, exp, jti replay), finds or creates the biobank identity, and sets our own HS256 session cookie, as paperKB does.Every cohort granted to provider:biobank, which means the three biobank cohorts.   • One check, everywhere. Each request goes through access.Resolve(session, cohort) before any cache lookup or job submission. A cohort the caller can't see answers 404, and it doesn't appear in listings or search.
  • Jobs carry the decision. The API puts the caller's resolved access in the job payload, and the worker checks it again against cohort_grants before reading vectors. A queued job can't outlive a revoked grant by more than one check.
  • Sample group import uses the signed-in user's biobank token, server to server, against the configured biobank base URL. Nothing about the API location comes from the request.

Privacy rules

Each cohort has a privacy profile, and every response that touches score values goes through internal/privacy with that profile. Handlers never serialize raw vectors themselves.

Ruleopen (1KG)protected (biobank)
Minimum group or cell size110 by default, configurable per cohort
Histogram and odds-ratio bins below the minimumShownMerged with a neighbour, or suppressed and labelled
Box plotsOutlier points and min/max shownNo outlier points. Whiskers at p1/p99.
Sample-level views (per-sample PCA/UMAP, sample lookup, per-sample CSV)AllowedNever
Sample IDs in responsesAllowed (they're public)Never
Differencing between overlapping groupsNot applicableCase and control must be disjoint, or the overlap is reported and dropped. Requests are audit-logged. Optionally, refuse a group whose symmetric difference with another of the user's groups is below the minimum.
  • Users cannot create groups from arbitrary ID lists on protected cohorts. Groups come from the biobank import or from admins.
  • The cache key includes the privacy profile, so a result computed under open rules can never be served for a protected cohort.
  • User-uploaded scores (later) produce a score set with visibility: owner. Only the uploader and admins see it, under the cohort's normal privacy profile.

Beyond parity (after v1)

  • Trait view: all PGS for an EFO trait side by side, with distributions, case/control separation, variant match rate, development ancestry, and the correlation between scores.
  • Portability: per-ancestry mean and variance shifts for every score, precomputed per cohort release.
  • Multivariate, done safely: a PGS × PGS correlation matrix per sample group, with clustering and PCA of the scores. These are aggregates, so they work on protected cohorts. On the open 1KG cohort, the per-sample PCA, UMAP and heatmap views can come back as they were.
  • Covariate-adjusted models (age, sex, PCs), if the biobank can supply covariates through the same server-side path.

Jobs and the queue

Everything runs in one muranoq namespace, pgsx. The app submits jobs with a submit account. The analysis workers and the Slurm delegate each use their own work account. Every job is tagged user:<id> and cohort:<slug>.

QueueWeightServed byLimits
interactive80Analysis workerstime_limit 60 s, no retries beyond 1
bulk20Analysis workersEvery bulk job shares concurrency_key: pgsx-bulk with a limit of 1
hpc(own workers)Slurm delegate onlyLong time_limit, lease TTL 30 min

muranoq never preempts a running task. So each analysis worker runs with Concurrency of 4 or more, and the pgsx-bulk concurrency key caps bulk work at one slot across the whole pool. An ingest therefore can't take every slot, and interactive requests always find a free one.

An analysis request, end to end.

  1. The API normalizes the request and checks cohort access, and computes its cache key (request, release, privacy profile, group member hashes).
  2. On a hit, it returns the cached result straight away.
  3. On a miss, it submits pgsx.analysis.* to interactive with idempotency_key set to the cache key, so identical concurrent requests share one job. It then waits up to about 3 s with client.Wait.
  4. If the job finishes in that time, the API returns the result inline. Otherwise it answers 202 with the job ID, and the page polls /api/v1/jobs/{id} (SSE later).
  5. The worker applies internal/privacy before writing the result, so nothing below the minimum cell size reaches the cache, muranoq or the browser.

The analysis worker. pgsx worker is built on the muranoq-go worker package. It creates a worker.New(client, worker.Config{Name, Concurrency, Capacity}), registers a handler for each type with w.Handle("pgsx.ingest", …), and runs w.Run(ctx). The SDK handles registration, claiming within free capacity, lease heartbeats, stop/cancel signals, and deregistration on SIGTERM. Handlers just decode the payload, use the task ref as their idempotency key, report progress with t.Progress(…), and return either a result or an error: worker.Terminal(err) for bad input, worker.Retry(err, d) for a retry after a delay. The API server uses muranoq-go/client to submit jobs (with an idempotency key and tags) and to read their state. Connection settings come from MURANOQ_URL and MURANOQ_TOKEN_FILE, or from the muranoq: block in pgsx.yaml.

Chaining. pgsc_calc → ingest → summarize runs as a dependency chain, or as follow-on jobs if muranoq's M2 lands first. Until then, a reconciler loop in pgsx worker watches the app's jobs rows and submits the next step. The same loop mirrors muranoq state into jobs for the UI, using events or SSE once muranoq has them and polling until then.

Adding new data (the new v1 feature):

  1. An admin runs pgsx cohort release create biobank-a, or picks an existing release.
  2. pgsx pgs compute --cohort biobank-a,biobank-b,1kg-30x --pgs PGS005000-PGS005200 (or the admin UI) submits one pgsx.hpc.pgsc_calc job with one task per cohort.
  3. The job gets as far as Slurm, and its progress shows on the admin Jobs page.
  4. Ingest and summarize run. The new scores appear in loading state, and an admin promotes them to active.
  5. For outputs already on S3 there's a direct path: pgsx ingest pgsc-calc s3://….

Slurm delegate

A cron job on the cluster polls muranoq, submits work to Slurm, and reports status at least every 10 minutes. There is no live heartbeat. Compute nodes never talk to muranoq; they read the cohort VCFs from the cluster filesystem and read and write S3.

     COMPLETED        → verify s3://…/runs/<ref>/_SUCCESS → complete {result: {s3_prefix, qc}}
     FAILED/TIMEOUT   → fail {retryable: true|false, error: tail of logs}
3. free = max_inflight − tracked
   claim {max: free, wait: 0}
   for each task: render sbatch from template (time = task.time_limit) → sbatch → save
     {ref, lease_token, slurm_id, submitted_at} to the state dir
  • SDK use: the delegate (pgsx slurm-delegate --once) uses muranoq-go/client directly, not the worker package. worker.Run and Close deregister the worker on exit, and muranoq hands a deregistered worker's tasks straight back to ready, which would undo every tick. Instead each tick calls RegisterWorker (idempotent) and never deregisters. It saves each client.Claimed (ref and lease token) to the state file and passes it back to Heartbeat, Complete or Fail on later ticks. client.IsLeaseLost tells it when a saved claim has expired.
  • Leases: the pgsx-slurm queue's namespace gets lease_ttl ≥ 3 × cron interval (30 minutes), so two missed ticks don't lose the lease.
  • Idempotency: the task ref names the S3 output prefix and the Slurm job name. A re-run finds and reuses a completed prefix instead of computing again.
  • pgsc_calc on Slurm: the sbatch job runs a Nextflow head process with -profile slurm, which fans out its own Slurm jobs. The delegate tracks the head job, and progress comes from Nextflow's trace file.
  • The pgsc_calc batch script (hpc/pgsc_calc.sbatch):
    1. Looks up the task's cohort in the delegate config (cohorts.<slug>.vcf, target_build) and writes the pgsc_calc samplesheet pointing at those VCFs in place. Nothing is copied.
    2. Stages the score matrix (if any) from S3 to scratch. It's already in pgsc_calc's own format and is passed through unchanged with --scorefile.
    3. Runs pgscatalog/pgsc_calc with --target_build, --pgs_id and/or --scorefile, plus --run_ancestry with the reference panel.
    4. Uploads results/ and a _SUCCESS marker to the run prefix, then cleans up scratch.
  • S3 credentials: the operator's credentials stay on the cluster, as now. Payloads carry only cohort slugs and S3 URIs, never filesystem paths or credentials.
  • Delegate config (pgsx.yaml on the cluster): the muranoq URL and token file, S3 bucket, max_inflight, the sbatch template, and a cohorts: map from slug to VCF path pattern and genome build. A task for an unknown slug fails as terminal.

What a muranoq delegate mode would add

The tick above works against muranoq as it is. These are the gaps that make a built-in mode worth adding once the cron script has settled the rules.

Gap with plain leasesProposed delegate behaviour
Lease TTL is set per namespace, so long TTLs also apply to ordinary workers.A worker registers with mode: delegate and a report_interval. The server sets that worker's lease TTL to about 3× the interval.
time_limit counts time spent waiting in Slurm's queue.Heartbeats carry an external_state of submitted or running, and the time limit clock starts at running. Queue wait gets its own optional limit.
If the cron dies, the lease expires and the task is retried while the Slurm job may still be running, so it can run twice.An expired delegate lease moves the task to orphaned instead of ready. The next tick from the same worker can adopt it again with the saved external_id; otherwise an operator releases it.
The Slurm job ID is invisible in muranoq status.The task records external_id and external_state, and status shows them.
Every site would write its own state-file glue.muranoq delegate --once --type … --submit 'sbatch …' --status 'sacct …' --cancel 'scancel {id}' --state-dir …. The same shape would work for PBS, LSF or Kubernetes Jobs.

Milestones

P0

Foundations

  • Repo skeleton in the paperKB shape: config, goose baseline, a /api/v1/session endpoint, admin users and API keys.
  • CI: gofmt, vet, lint, test and a migrate-check.
  • Kustomize manifests for Jetstream2 Kubernetes: API, frontend, worker, muranoq (from muranoq's deploy/k8s), Postgres and ingress. docker-compose for local dev.

Exit: an empty app deploys to Jetstream2 and an admin can log in with a local password.

P1

Data layer

  • Cohorts, releases, samples, sample groups, score vectors, and cohort_grants.
  • pgsx ingest wide and pgsx ingest pgsc-calc.
  • PGS Catalog sync, the 1KG 30× open cohort with population groups, and the current biobank data loaded into its cohort(s).

Exit: 1KG and the biobank cohorts are loaded, and vector reads are benchmarked.

P2

Analysis parity

  • internal/stats with scipy-checked fixtures.
  • The privacy gate.
  • Distribution and case-vs-control endpoints and pages, the score detail page, and the results cache.

Exit: the open 1KG cohort works end to end with no login, which is enough to show for the paper.

P3

Biobank access

  • Biobank JWT login via JWKS, the provider:biobank grant, and the access check on every route and job.
  • CILogon login and admin grants to individual users.
  • Server-to-server sample group import, group management, and the audit log.

Exit: a biobank user reproduces today's analyses on a biobank cohort, and an anonymous user can't tell those cohorts exist.

P4

Queue and Slurm

  • pgsx worker on the muranoq-go worker package, the ingest and summarize handlers, and the reconciler.
  • The pgsx slurm-delegate cron job and the pgsc_calc sbatch template.
  • pgsc_calc per cohort → S3 → ingest. Admin pages for jobs and cohorts.

Exit: an admin adds 100 new PGS from the CLI and they appear after promotion.

P5

Cutover

  • Run the new site side by side with the old one and compare numbers for a fixed set of PGS.
  • Switch DNS and retire the old site.

Exit: pgsviz.compgenlab.org serves the new app.

P6

Beyond parity

  • Trait comparison, portability, aggregate multivariate views (and sample-level ones on 1KG), and OAuth2 data return to the biobank.
  • Users uploading their own score matrix to run against cohorts they can access.
  • A muranoq delegate mode, if the cron job shows the need.

Exit: scoped separately.

Open questions

  1. Name: PGS Atlas, PGS Visualizer, or something else? See Name. The binary, config and job-type prefix follow the choice.
  2. Biobank JWT details: the issuer, the JWKS URL, the audience, and how login starts (a redirect that carries the token, or a POST from the biobank site). It would also help to know whether the token says anything about which of the three cohorts the user works with, or whether "any valid login" stays the rule.
  3. Current data: today's 37,948 samples are one pool. Which of the three biobank cohorts does each sample belong to, and do all three cohorts already have scores?
  4. Biobank participant lists: can one list span several cohorts? If so, should an import split it into one group per cohort, or should the user pick one cohort?
  5. Data return format: which score types per PGS (SUM, Z_norm2, percentile…), and what the biobank's ingest endpoint expects.
  6. User score uploads (later): should a run need admin approval, and what quota applies (for example, the number of scores per upload and runs per month)?
  7. Kubernetes on Jetstream2: Postgres in the cluster (CloudNativePG) or a managed or VM instance? And which ingress does the cluster use?
